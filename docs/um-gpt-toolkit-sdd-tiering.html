In this catalog, the planner is the bill.

Intuition says the bill flips between tiers depending on which builder you pick. Even with cache discounts applied everywhere, it doesn't flip — because caching only touches input, and the planner's cost is dominated by output, which no cache discounts:

SOL $30 ÷ nano $0.40 = 75x → planner is 95% of spend SOL $30 ÷ Kimi $3.00 = 10x → planner is 72% 5.1 planner $0.35 vs Kimi builder $0.46 → flipped, barely

The consequence cuts both ways.

Downward: builder price is noise — the four builder seats above span $0.07 to $0.46 on a ~$1.60 job. Pick the builder on capability and cache behavior, never on rate.

Upward: planner tokens are the only line worth engineering, and specifically planner output: review as diffs, verdict-plus-findings formats, no restating the spec back.

The one configuration that reaches the flip is GPT-5.1 as a value planner — at $1.25 / $0.125 cached / $10 it's frontier-family judgment priced like a mid-tier. Whether its review gate is strict enough for that seat is an empirical question, not a pricing one.

Effort levels by seat Reasoning effort bills as output tokens — the one line caching never discounts, and the line this page shows dominating planner cost. That makes effort a direct multiplier on the largest number in the stack, worth setting per seat rather than left at defaults:
  • Planner: high for decomposition and spec-writing (few calls, maximum leverage per token), medium for routine diff review, escalating only when a diff gets flagged. High effort on mechanical approvals is the quiet budget leak.
  • Batch QA: high, always — tolerating effort-driven latency off the interactive path is why the seat exists.
  • Builder / Builder+: minimal, or thinking off. A builder burning reasoning tokens against a prescriptive spec pays planner-shaped costs at builder rates — and a builder reasoning its way around the spec is precisely the drift the review gate exists to catch.
  • Value planner: medium by default; the seat's economics only work below flagship effort.
Two caveats. Effort knobs (reasoning_effort, thinking budgets, thinking levels) are API-level parameters, so whether U-M GPT Toolkit users can set them depends on the user's path — a verify-with-ITS item. Published cost and speed benchmarks are measured at specific effort settings, why this page carries no speed column. The Effort column in the ladder shows the recommended default for each row's seat; n/a marks non-reasoning models.
Kimi K2.5 and gemini-3-flash-preview, one row apart gemini-3-flash-preview at $0.50 / $0.05 / $3.00 and Kimi K2.5 at $0.60 / $0.10 / $3.00 occupy the same Builder+ seat, a dime apart on base input and a nickel apart on cache reads. The differences that remain are mechanics, not list price:
  • Cache behavior. Kimi's caching is automatic and flat — no configuration, no storage meter. Gemini's explicit caching reads cheaper at $0.05 but adds a storage meter (~$1.00 per 1M tokens per hour held); its implicit caching discounts automatically without one. For a steady agent loop the two land ahead-or-even of each other depending on prefix stability and cache lifetime.
  • Output rate is identical, and output dominates builder cost at these volumes — so the seat's real bill is the same either way.

So the honest framing for a U-M department build: the two are price-equivalent within noise. Choose between them on capability fit for the workload — a bake-off question, not a pricing one.

Cache fine print that changes billing
  • Minimums and matching. Azure OpenAI caching needs a 1,024-token minimum with an identical prefix — reads are automatic, discounts land only if stable content leads the prompt.
  • Writes aren't always free. GPT-5.6-generation models bill cache writes at 1.25x input (older OpenAI models write free). Claude bills writes at 1.25x (5-min) or 2x (1-hr). Gemini explicit caching bills storage per hour.
  • GPT-5.6 caching is still maturing on Azure. The published caching support matrix doesn't yet list the 5.6 family, and cache reads currently land via Chat Completions but not the Responses API. Cached rates shown for SOL / TERRA / LUNA ($0.50 / $0.25 / $0.10) are OpenAI-documented read rates. Update when more information for newest models land.

Token volumes and cache-hit rates in the six-way comparison are illustrative assumptions, labeled above, not measured. Cache-hit modeling: builders 70% of input at cached rate, planner and solo 50%; cache-write premiums and storage meters excluded for simplicity and noted above.

A speed column is intentionally excluded. Published throughput benchmarks (e.g. Artificial Analysis) measure first-party APIs at specific reasoning-effort settings, not U-M GPT Toolkit deployments; reasoning-model latency varies with effort level. Mixed-source tokens-per-second figures would be false precision for capacity planning here.

Embedding models from the U-M ITS page are omitted: a spec-driven build/review harness assembles context from repo files and search rather than an embedding index. Use them only if the harness includes a RAG retrieval layer.
