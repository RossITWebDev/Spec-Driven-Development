What is Spec-Driven Development?

Spec-Driven Development (SDD) is a spec-first approach in which teams define requirements, constraints, guardrails, acceptance criteria, and edge cases before implementation. AI then uses that shared specification to generate code, tests, documentation, and other supporting artifacts from the well-defined context.

The specification serves as the common source of truth throughout the development lifecycle, connecting business objectives to architecture, implementation, testing, and validation. By anchoring every stage to the same context, AI-generated outputs remain consistent, traceable, and aligned with the original intent.

In this catalog, the planner is the bill.

Intuition says the bill flips between tiers depending on which builder you pick. Even with cache estimate discounts applied everywhere, it doesn't flip — because caching only touches input, and the planner's cost is dominated by output, which no cache discounts:

SOL $30 ÷ nano $0.40 = 75x → planner is 95% of spend SOL $30 ÷ Kimi $3.00 = 10x → planner is 72% TERRA $12 ÷ LUNA $1.20 = 10x → planner is 73% 5.1 planner $0.35 vs Kimi builder $0.46 → flipped, barely

The July 30 price cut is the cleanest test this page has had. OpenAI cut a builder-seat model 80% and a planner-seat model 20%. The 20% planner cut is what moved the illustrated bill: TERRA → nano fell from $0.65 to $0.53. The 80% builder cut is what made LUNA viable as a builder seat at all — it took that seat from $0.87 to $0.17 — but swapping nano for LUNA still only moves a ~$0.60 job by a dime.

The consequence cuts both ways.

Downward: builder price is noise — the builder seats above span $0.07 to $0.46 on jobs from $0.53 to $1.62. Choose the lowest-effective-cost builder that meets measured quality, latency, reliability, and governance requirements.

Upward: Planner output is a high-leverage optimization target, alongside context retrieval, cache writes, builder retries, and review cycles.

The value-planner seat now has two credible occupants. GPT-5.1 at $1.25 / $0.125 cached (estimate) / $10 is still the cheapest planner on the board at $0.35 for the illustrated workload. Claude Sonnet 5 at $2.00 / $0.20 / $10 matches that output rate from a current-generation tier, which is why it lands at $0.41 and beats TERRA's $0.47 despite an identical input rate — TERRA's $12 output is the whole difference. Whether either review gate is strict enough for the seat is an empirical question, not a pricing one.

Effort levels by seat
Reasoning effort bills as output tokens — the one line caching never discounts, and the line this page shows dominating planner cost. That makes effort a direct multiplier on the largest number in the stack, worth setting per seat rather than left at defaults:
  • Planner: high for decomposition and spec-writing (few calls, maximum leverage per token), medium for routine diff review, escalating only when a diff gets flagged. High effort on mechanical approvals is the quiet budget leak.
  • Batch QA: high, always — tolerating effort-driven latency off the interactive path is why the seat exists.
  • Builder / Builder+: minimal, or thinking off. A builder burning reasoning tokens against a prescriptive spec pays planner-shaped costs at builder rates — and a builder reasoning its way around the spec is precisely the drift the review gate exists to catch. This now needs an explicit setting on LUNA: its documented effort range is none / low / medium / high / xhigh / max with medium as the default, so a builder left at defaults is a reasoning model billing reasoning output. Set it to none or low.
  • Value planner: medium by default; the seat's economics only work below flagship effort.
  • Claude planners and reviewers: Opus 5 runs thinking by default rather than on request, and its effort ladder tops out above the point where thinking can be disabled. Budgets carried over from an Opus 4.x deployment will under-forecast output on identical prompts.
Two caveats. Effort knobs (reasoning_effort, thinking budgets, thinking levels) are API-level parameters, so whether U-M GPT Toolkit users can set them depends on the user's custom path or coding harness. Published cost and speed benchmarks are measured at specific effort settings, why this page carries no speed column. The Effort column in the ladder shows the recommended default for each row's seat; n/a marks non-reasoning models.
The Builder+ seat has a new floor
gemini-3-flash-preview at $0.50 / $0.05 / $3.00 and Kimi K2.5 at $0.60 / $0.10 / $3.00 still occupy the same Builder+ seat, a dime apart on base input and a nickel apart on estimated cache reads. What changed in July is that GPT-5.6-LUNA at $0.20 / $0.02 / $1.20 now undercuts both on all three lines — roughly 2.5x cheaper on the builder seat as modeled above. The remaining differences are mechanics and fit, not list price:
  • Estimated cache behavior. Kimi's caching is automatic and flat — no configuration, no storage meter. Gemini's explicit caching reads cheaper at $0.05 but adds a storage meter (~$1.00 per 1M tokens per hour held); its implicit caching estimate discounts automatically without one. LUNA's caching is automatic with explicit breakpoints available and a 30-minute minimum cache life, and its writes bill at 1.25x input.
  • Gemini and Kimi share an identical output rate, and output dominates builder cost at these volumes — so between those two the seat's real bill is the same either way.
  • Price is no longer the reason to pick Gemini or Kimi over LUNA. Capability fit, latency under load, multimodal need, vendor concentration, and data-handling posture are — and those are testing and governance questions.

So the honest framing for a U-M department build: gemini-3-flash-preview and Kimi K2.5 are price-equivalent within noise, and both now carry a real price premium over LUNA that has to be justified on something other than the rate card.

Cache estimates fine print that changes billing
  • Minimums and matching. Older Azure OpenAI caching needs a 1,024-token minimum with an identical prefix — reads are automatic, discounts land only if stable content leads the prompt. The GPT-5.6 generation adds explicit cache breakpoints and a 30-minute minimum cache life, which makes cache behavior more predictable across an agent loop.
  • Writes aren't always free. GPT-5.6-generation models bill cache estimate writes at 1.25x input (older OpenAI models write free). Claude bills writes at 1.25x (5-min) or 2x (1-hr). Gemini explicit caching bills storage per hour. Claude's cacheable minimum also moved: Opus 5 caches from 512 tokens where Opus 4.8 needed 2,048, so short system prompts and tool schemas now cache where they previously did not.
  • The long-context meter can double your input line. GPT-5.6 requests above 272K input tokens bill input and cached input at 2x and output at 1.5x for the entire request — SOL becomes $10 / $45, TERRA $4 / $18, LUNA $0.40 / $1.80. A repo-scale spec harness that assembles context aggressively can cross that threshold without anyone choosing to, which is a retrieval-discipline problem before it is a pricing one.
  • Azure documentation now describes GPT-5.6 caching for both Chat Completions and Responses, including prompt_cache_key. Whether U-M Toolkit exposes the same behavior, reporting fields, and billing treatment should be confirmed through Toolkit telemetry or ITS documentation.
Housekeeping the ladder implies

Three additions are worth a policy line rather than a footnote. A speed column is intentionally excluded. Published throughput benchmarks (e.g. Artificial Analysis) measure first-party APIs at specific reasoning-effort settings, not U-M GPT Toolkit deployments; reasoning-model latency varies with effort level. Mixed-source tokens-per-second figures would be false precision for capacity planning here.

Model classes on the ITS Toolkit table but omitted here: embedding models (Ada, text-embedding-3-small, text-embedding-3-large), because a spec-driven build/review harness assembles context from repo files and search rather than an embedding index — use them only if the harness includes a RAG retrieval layer; image models (gpt-image-2, gpt-image-1.5, gemini-3.1-flash-image-preview) and gpt-realtime-2, because an SDD text harness does not call them and their per-token rates are not comparable to text rates.
